ОБЩИЕ ПРАВИЛА

Стиль кода

- Свойства классов только для чтения через =>, без явных блоков get / set и автосвойств. Изменение выполнять отдельным методом с необходимой валидацией; расчёты и проверки не прятать в свойства.
- Не использовать ?? и ??= для проверки null или подстановки замены. Только явный if (value == null). Вызов события ?.Invoke() разрешён.
- избавиться от тернарников и ? проверок по типу Weapon weapn = GetWeapon ? null вот такую хуйню, а по типу ?.Invoke() не трогать, так проверять можно.

- Вложенные классы не использовать. Каждый класс объявлять отдельно и размещать в собственном файле.
- Не использовать явное сравнение с true: вместо if (condition == true) писать if (condition).
- Явное сравнение с false допустимо: if (condition == false).
- Полностью запретить FormerlySerializedAs в собственном коде проекта. Существующие использования удалить при рефакторинге.
- Работать только с актуальными системами и форматами, без legacy-миграций и совместимости со старыми именами полей.
- При переименовании сериализованных полей напрямую обновлять текущие сцены, префабы и SO, сохраняя необходимые актуальные значения и ссылки. Не оставлять старые поля или алиасы ради совместимости.

ScriptableObject / TierTable

- НИКАКОЙ ЛОГИКИ В СО, ЭТО ТОЛЬКО АССЕТ С ДАННЫМИ!!!
- без вложенных классов
- SO хранит сериализованные данные и предоставляет простые свойства чтения без расчётов.
- Расчёты, поиск записей, сортировку и проверку запросов выполняет использующая данные система.
- Не создавать обязательный отдельный класс чтения/обёртку для каждого SO. Самостоятельный расчётчик или валидатор выделять по ответственности и необходимости переиспользования.
- Убрать sealed из собственных классов проекта. Это принятое правило стиля автора, а не оптимизация производительности или сокращение игровой логики.
- Убрать readonly у приватных полей собственных классов проекта. Не использовать его только для обозначения того, что поле не предполагается переназначать.

СОХРАНЕНИЯ И АДАПТЕРЫ

PlayerProgress → Saver

- Удалить PlayerProgress как дублирующую обёртку.
- Создать обычный класс Saver — единый сервис доступа к сохранениям.
- Saver реализует узкие интерфейсы для подсистем. Каждый потребитель получает только необходимый контракт.
- Чтение и изменение — отдельные методы. Методы чтения ничего не меняют.
- Каждый метод изменения сразу инициирует сохранение. Отдельный публичный Save() потребителям не нужен.
- Связанные изменения сохранять одной операцией: например, обе громкости или результат завершения уровня.
- Игровые правила и расчёты остаются в подсистемах. Saver сохраняет переданные результаты, а не определяет покупки, награды или исход рулетки.
- Не отдавать наружу изменяемые списки сейва. Изменения проводить через методы сервиса.
- SavesYG оставить структурой данных с корректными начальными значениями.
- Yg2SavesAccess оставить адаптером платформенного хранения; доступ к YG2 скрыть от потребителей.
- Полностью удалить legacy-поля, миграции и числовые индексы скинов.
- Сохранить проверку готовности данных. Не допускать молчаливого пропуска записи до инициализации.
- Для операций, требующих подтверждённого сохранения перед анимацией, предусмотреть ожидание результата записи и обработку ошибки в адаптере.
- Не создавать дополнительные классы сохранения без самостоятельной обязанности.

Исходное требование:

- Полностью избавиться от легаси в проекте, все на новые системы.
- убрать класс плеер прогресс
- сделать отдельный сервис сохранения с публичным апи под интерфейсами

СЕССИИ, ПЕРЕХОДЫ И ПАУЗА

SessionHandler — ответственность хендлеров сессий

Назначение

- Каждый хендлер координирует сценарий своей сцены. Он даёт команды подсистемам и обрабатывает их результаты, а не реализует их внутренние алгоритмы.
- Поток подготовки, запуска и завершения должен быть явным и линейным, читаемым сверху вниз.
- Хендлеры сцен остаются отдельными классами. Общий интерфейс жизненного цикла, базовый класс и декораторы без конкретного потребителя или общей реализации не вводить.

Подготовка и запуск

- Предоставить явные методы подготовки, запуска и завершения сессии, вызываемые сценовым навигатором.
- Подготавливать системы сцены через их API. Генерацию уровня целиком делегировать LevelGenerator: хендлер не рассчитывает размещение и не спавнит предметы самостоятельно.
- Запускать нужные системы, включая Movement, ItemCollector и музыку, в соответствии со сценарием сцены.
- Передавать плейлист сцены через IMusicPlayer. Дальнейшим проигрыванием и плавными переходами управляет аудиосервис.

Пауза и продолжение

- Хендлер — единственная точка управления приостановкой и возобновлением геймплея текущей сессии.
- UI и другие инициаторы обращаются к хендлеру с запросом. Окна не получают прямой доступ к Pauser и не ставят паузу самостоятельно.
- Внутренний Pauser учитывает активные запросы; хендлер применяет итоговое состояние к системам сцены.
- Сохранить текущую логику счётчика запросов Pauser. Объекты запросов и новую систему причин паузы не вводить.
- Каждый инициатор освобождает только собственный запрос. Продолжать геймплей, когда запросов больше нет и состояние сессии допускает продолжение.
- Приостанавливать движение, поглощение и игровые анимации; не заставлять каждый обработчик предмета проверять паузу.
- Различать паузу и завершение. Снятие паузы не запускает уже завершённую сессию и не сбрасывает активный адреналин.
- Сохранить существующий учёт внешней паузы. Текущая логика Pauser устраивает автора; отдельный редизайн учёта запросов не требуется.

Сценарий Game

- Следить за оставшимся временем через уведомления таймера и сравнивать остаток с порогом из конфига сессии.
- Когда время ниже порога, один раз включать адреналин и виньетку. Текущее значение порога — 20 секунд, а не число в коде.
- Обрабатывать завершение игрового сценария, останавливать соответствующие системы и инициировать следующий переход.
- При завершении выключать эффекты; при новом запуске сбрасывать состояние их активации.

Сценарий Fill

- Обращаться к системе заливки за рассчитанным результатом.
- До анимации командовать Rewarder начислить награду, обновлять прогресс через соответствующие системы и инициировать сохранение через Saver.
- Для гарантии сохранённого результата до показа дожидаться подтверждения записи, если операция асинхронная.
- После фиксации результата запускать визуальный показ. Прерывание анимации не отменяет результат и не вызывает повторное начисление.
- Обрабатывать команды продолжения, перезапуска, выхода и спасения через соответствующие системы. После подтверждённой рекламной награды или технической ошибки показа доплачивать разницу до полной награды уровня.

Сценарии Menu и Shop

- Хендлер меню обрабатывает намерения пользователя, инициирует переходы, организует открытие окон через UI-фабрику и решает, когда показывать daily.
- Хендлер магазина управляет жизненным циклом сессии магазина и выходом из него. ShopPanel занимается только навигацией страниц.
- Покупки улучшений, выбор скина и операции рулетки остаются в собственных подсистемах, а не собираются в хендлере магазина.

UI, завершение и переходы

- Создание окон делегировать фабрике; передавать необходимые данные до показа. Освобождение выполняет назначенный владелец жизненного цикла.
- При выходе завершать работу систем и принадлежащих сценарию незавершённых действий. Не оставлять отложенные действия старой сессии выполнять новый сценарий.
- Инициировать переходы через явные методы SceneNavigator. Загрузку и выгрузку сцен, экран загрузки и защиту от повторного перехода выполняет навигатор.

Граница ответственности

- Хендлер определяет последовательность и момент вызова, но делегирует расчёты и исполнение.
- В хендлер не переносить алгоритмы движения, поглощения, сетки, генерации, расчёта награды, покупки, записи в YG2 и покадровой анимации.
- Отдельный узкий контракт запросов паузы для UI допустим: он не даёт доступа к запуску, завершению или переходам всей сессии.

Финальный отсчёт: адреналин и виньетка

- Таймер только отсчитывает время и сообщает об изменении остатка, остановке и завершении; порог финального отсчёта ему не принадлежит.
- Хендлер сессии следит за оставшимся временем и сравнивает его с порогом из конфига сессии.
- Порог задаётся длительностью, а не процентом. Текущее значение — 20 секунд, без числа, зашитого в код.
- Когда остаток меньше порога, хендлер один раз включает адреналин и запускает виньетку.
- Адреналин и виньетка не следят за таймером и не знают друг о друге.
- Повторные уведомления времени не запускают эффекты заново.
- При завершении сессии хендлер выключает эффекты и возвращает множитель скорости к 1. При новом запуске сбрасывается состояние их активации.
- Пауза не является завершением сессии и не сбрасывает адреналин.

Movement / Mover

- Mover - требует жесточайшего упрощения.
- Пусть он просто двигается в нужном направлении, скорость ему передается в методе, большего он знать не должен. движение линейное.
- Mover рассчитывает шаг из направления и переданной скорости, получает предполагаемую позицию и передаёт её Clamper до перемещения.
- Clamper — отдельный класс ограничения движения. Возвращает допустимую позицию через ClampPosition(desiredPosition), а не true/false для всего шага.
- Mover применяет скорректированную позицию. Это позволяет дойти до края частичным шагом и двигаться вдоль границы.
- Границы передаются Clamper извне при подготовке уровня. Movement не рассчитывает перемещение и не проверяет карту.
- коллайдер ему вообще не нужен как и прочие конфиги.

- Выделить отдельную систему Movement с одноименным скриптом во главе
- он хранит в себе мувер, ротатор и переключатель скорости. это даст простой и удобный интерфейс для взаимодействия. просто передаешь нужное направление и он двигает куда надо.
- Паттерн фасад.
- Мовемент имеет открытое апи, включить управление, отключить управление
- Movement получает базовую скорость от системы тиров игрока.
- Итоговая скорость = базовая скорость × множитель адреналина; готовое значение передаётся в Mover.
- Без адреналина множитель равен 1. Значение ускорения берётся из конфига адреналина.
- При смене тира активный множитель применяется к новой базовой скорости. Повторное включение не накапливает множитель.

ПРЕДМЕТЫ И ГЕНЕРАЦИЯ УРОВНЯ

ItemCollector — система поглощения

- Создать фасад-оркестратор ItemCollector, предоставляющий единую точку управления поглощением.
- Внутри разделить обнаружение, проверку доступности, притяжение, захват и анимацию поглощения. Не переносить все алгоритмы в сам фасад.
- Предоставить команды запуска и остановки работы. Отдельно определить поведение при паузе и завершении: приостановка сохраняет процесс для продолжения, окончательная остановка завершает или отменяет его.
- Исключить повторный захват одного предмета.
- Предоставить событие ItemCollected с данными собранного предмета.
- Зафиксировать момент сбора и гарантировать однократное уведомление. Анимация не должна приводить к потере или повторному учёту предмета.
- Не помещать внутрь квоту, начисление наград, рост игрока и воспроизведение звука. Эти системы реагируют на событие сбора.

Общее правило доступности поглощения

- Выделить общую проверку CanCollect(item).
- Использовать её в поглощении, притяжении и переключении прозрачности.
- Учитывать тир игрока, тир предмета и соответствующие улучшения.
- Не дублировать сравнение тиров в каждом компоненте.

ЗАЛИВКА ФОРМЫ

FillOrchestrator / модель / представление / награда

1. FillOrchestrator — фасад и презентер. Управляет подготовкой, запуском показа, ускорением и дозаполнением.

2. Модель заливки — данные результата. Сетка, количество кубиков, итоговый процент, победа/проигрыш и награда. Расчёты делегировать небольшим классам с конкретными обязанностями.

3. Представление — визуальное выполнение. Подложка, контур, создание и полёт кубиков, отображение процента. Получает готовые данные и не меняет деньги или прогресс.

4. Сессионный хендлер фиксирует результат до анимации. Получает рассчитанный результат, командует Rewarder начислить деньги, обновляет прогресс и инициирует сохранение. Только после этого запускается показ.

5. Начисление защитить от повторного выполнения. Повторный запуск показа не выдаёт награду снова. После спасения доплатить разницу между полной наградой уровня и уже начисленной суммой.

Награда после спасения

- При успешном спасении после рекламной награды или при технической ошибке показа итоговый заработок за уровень становится равен полной награде, а не частичной плюс полной.
- Пример: ранее начислено 10, полная награда — 50. Начислить ещё 40; итоговый заработок за уровень — 50.
- Зафиксировать доплату и результат через Saver до показа дозаполнения и изменения суммы.
- В окне результата анимировать увеличение показанной награды с 10 до 50. Анимация только отображает уже начисленную сумму.
- Повторный callback рекламы, повторный показ окна или анимации не должны повторно начислять доплату.

6. Звук вынести в подписчики событий. FlyingCubeArrivalSound получает прогресс показа, рассчитывает возрастающий pitch и обращается к IGameSoundPlayer. Ограничение частоты выполняет аудиосервис.

Цепочка:

Рассчитать результат
→ начислить награду и обновить прогресс
→ сохранить
→ показать заполнение
→ показать уже заработанную награду

Закрытие вкладки во время анимации не должно отменять результат. Для этого сохранение выполняется заранее; если оно асинхронное, для гарантии нужно дождаться подтверждения записи, а не просто вызвать Save().

- При подтверждённой награде или технической ошибке показа рекламы закрыть окно через владельца жизненного цикла и запустить спасение с доплатой до полной награды. При ошибке не требовать повторной попытки или дополнительных действий игрока.
- Если реклама завершилась без подтверждённой награды, не выполнять спасение и оставить кнопку выключенной. Окно остаётся открытым; перезапуск и выход остаются доступными.

- Различать подтверждение награды, завершение без награды и техническую ошибку. Не определять исход только по отсутствию награды и не объединять все случаи в общий OnRejected.
- Отклонение запроса, например из-за уже показываемой рекламы, само по себе не является технической ошибкой рекламного показа и не должно автоматически давать спасение.
- Защитить сценарий от повторных колбэков: ошибка, последующее закрытие или повторное подтверждение не запускают второе спасение и повторную доплату.

РУЛЕТКА

RouletteService — 552 строки, 7 переплетённых обязанностей: экономика круток, таймеры, лут-RNG, выдача призов, витрина, запросы к каталогу, валидация конфига. Отвечать за него невозможно. Правила игры протекают во вью (_allSkinsCollected считается во вью, вью читает device clock). Приз выдаётся на остановке колеса — при закрытии вкладки в WebGL монеты списаны, приз потерян. Ежедневная и скинная рулетки — одна суть с разной настройкой, но написаны как две игры в одном классе.

Целевая схема

Суть обеих рулеток едина: слоты → доступ → взвешенный ролл → «слот → приз» → грант. Различия — три инжектируемых параметра, не типы.

RouletteModel

RouletteModel — один класс, без наследников и без базового класса. Два инстанса в скоупе DI: ежедневная и скинная.

- Внутри — синхронная транзакция Spin: проверка доступа → списание → ролл → грант → Save. Возвращает исход: индекс слота + приз.
- Запросы для UI: цена, остаток бесплатной крутки, остаток рекламных круток, доступность крутки.
- Инжектируемые различия: наполнение слотов (секторы конфига / витрина), способы доступа (бесплатно + реклама / монеты с прогрессивной ценой), правило «слот → приз» (секретный слот → случайный эксклюзив или компенсация / дубликат → компенсация).
- Источник правды — сейвы. Никакого зеркала сейвов в памяти.

RoulettePresenter

RoulettePresenter — один класс, два инстанса. Только секвенирование, ноль правил:

- состояния кнопок и таймерные тексты — из данных модели;
- рекламная крутка: реклама показывается ДО транзакции, Spin только после granted-колбэка;
- после Spin: анимация колеса к исходу → пауза → попап выигрыша → освобождение попапа.

RouletteView

RouletteView — удаляется на данном этапе, пересоздаётся тупой одновременно с презентером.

- без Mode-энума — одно окно на обе рулетки;
- без правил и без времени: состояния кнопок и таймерный лейбл приходят от презентера, наружу — только события кнопок;
- префаб не трогается, ссылки перевешиваются на новый класс.

RouletteWheel

RouletteWheel — остаётся, в нём остаётся только анимация.

- контракт: внутрь — индекс цели, наружу — события Tick (пересёк сектор) и Completed (визуальная остановка);
- тики звука уходят: колесо кидает Tick, отдельный скрипт подписывается и обращается к сервису звука;
- задержка на выигрышном секторе уходит презентеру;
- анимационная начинка (откат, докрут-отклонение, кастомный изин) не трогается — это филлинг.

RouletteWinPopup

RouletteWinPopup — переводится на систему юай (спавнер по запросу, слой попап).

- сам себя не уничтожает: рендерит приз, кидает Closed;
- освобождение через спавнер — тем, кто заспавнил, то есть презентером;
- рамки/плашки редкости, показ скина/монет — остаются как есть.

Помощники

Помощники:

- LootRoller — чистый RNG без сейвов;
- SkinInventory — «открыт/выдать» над OpenSkinIds (забирает дубль прямого доступа к сейвам из ShopPanel);
- SkinShowcase — квоты витрины, пересборка слотов;
- валидатор конфига — отдельный класс, вызывается один раз при регистрации в скоупе; конфиг остаётся чистыми данными.

Ключевые решения

1. Грант внутри Spin, до анимации. Анимация и попап — демонстрация свершившегося факта. Убивает потерю приза при закрытии вкладки и класс багов «выключил игру во время прокрутки — награда потеряна».
2. Реклама — до транзакции, не внутри модели: модель синхронна, показ рекламы — асинхронная платформенная церемония презентера.
3. Один класс, а не базовый класс с наследниками: различия — конфигурация зависимостей, а не типы. Наследники дали бы двух пустых детей.
4. Презентер без правил: любое «что делать дальше» — из данных модели.
5. МВП обоснован для рулетки как паттерн, не догма для всех окон.

Что удаляется

RouletteService целиком, включая прокси над кошельком; Mode-энум и форки по нему; _allSkinsCollected и GetNowUnixTime из вью; прямой доступ ShopPanel к сейвам скинов — через SkinInventory.
